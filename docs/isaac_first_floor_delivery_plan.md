## What every delivery must provide

1. **A cumulative change to the main DeathWard game.** Use `deathward`, the normal Game/Simulation path and the expedition's rooms, combat, inventory and rewards. Accepted behavior stays enabled and is exercised by later deliveries. A private review executable, manually spawned demonstration or unused reference helper does not complete a delivery.
2. **Immediate access.** Launch the main game directly into the expedition, with an identified repeatable seed/profile and an easy retry after death. Quick access may shorten travel to the feature; the same feature must also occur through ordinary room generation, acquisition and progression. Each handoff includes an exact tested launch command and opens the game when requested.
3. **A short human check.** Give at most three plain-language actions and an expected observable outcome. Most checks should take about 1–3 minutes; a boss or complete floor can take longer. The developer measures values and timing; the user is not asked to infer world units per second or do research.
4. **Source comparison before the handoff.** Reuse pinned XML, existing native captures and the running Isaac instance. Check the relevant arithmetic, timing and actual gameplay path. Research is limited to a named unresolved requirement for the delivery; it is not a separate deliverable.
5. **Live tuning, export and next-expedition loading.** Every new tunable parameter ships with the controls, application semantics, validation and persistence described below. An editable field that does not affect its real gameplay consumer fails the delivery.
6. **A checkpoint before expanding scope.** Record developer verification and the user's verdict separately. After a failed human check, correct that delivery before stacking dependent behavior on it. The user can authorize one delivery or a named range; preparing this plan does not authorize automatic bulk implementation.

## Meaning of 1:1

The target is the non-excepted behavior of installed **The Binding of Isaac: Repentance 1.7.9b**, ordinary Isaac on Normal. Start comparison coverage with Basement I, then cover eligible alternate opening floors before claiming all opening-floor coverage. Record the installation's actual unlock profile, starting equipment and applicable modifiers. The current live snapshot did not establish difficulty, stage or unlocks, so do not infer them from room appearance or an empty item sheet.

Preserve the user's isometric presentation, existing eight-direction movement/firing and mouse/keyboard mapping, and universal dodge including boost/immunity. Accepted immediate stopping also remains protected; D02 must explicitly distinguish matched movement pace from this stopping adaptation. A change to that exception requires its own selection. These exceptions prevent a literal claim of identical overall combat difficulty.

For everything else, match the source rule and outcome: runtime stats, timings, motion, collision eligibility, enemy behavior, rewards, item effects, counts and placement rules. Existing accepted-feel walking/shooting values are comparison checkpoints, not authority over the source target. Any adjustment away from those accepted values must be part of the selected delivery and its human review.

Freeze a recorded source floor for exact layout/content comparisons. Procedural acceptance additionally requires the source eligibility, graph, selection and placement rules; one matching floor does not prove generation. Identical Isaac seed-text compatibility is not established and must not be claimed. A narrowed item/enemy pool is a development state, never full first-floor acceptance.

## Live tuning and reusable presets

**D01 supplies this foundation; every subsequent delivery extends it.**

- Put a tuning panel in the main game's pause/review controls. Show the active preset, source value, override and actual effective value. Use familiar source stats such as Speed 1, Damage 3.5 and Range in tiles; keep spatial/timing conversions in an advanced view. Do not display stored Damage 3.5 as effective attack damage while shots still use 24.
- Keep a versioned reference preset and explicit custom overrides. `Reset to reference`, `Apply`, `Export preset`, `Load preset` and `Use for next expedition` must work. Custom overrides carry a visible Custom label; export does not certify them as Isaac-equivalent. Before complete acceptance, label reference coverage as partial.
- Export a human-readable, versioned **JSON preset** containing a self-contained resolved configuration plus overrides, schema version, content/build compatibility identifiers, source-version provenance and retained exceptions. A preset must reproduce the same effective values without depending on unsaved editor state. Remember the chosen next-expedition preset across application restarts; do not silently fall back to defaults. Seed and random-stream state belong to session/replay metadata, not hidden balancing changes.
- Loading validates the whole candidate, then publishes one consistent immutable configuration revision. Reject malformed, out-of-range or incompatible values with a clear error and preserve the active settings. Existing actors must not retain dangling references to replaced content. Reuse `MechanicsLibrary` loading/fingerprints where appropriate; existing immutable-loader tests do not constitute an in-game tuning UI.
- Saves/checkpoints identify the configuration they used. Loading a tuning preset changes configuration, not accumulated player inventory, current health, purchased stock, cleared rooms or RNG history. Changing a base stat recomputes applicable owned-item modifiers in the correct order instead of overwriting the final stat or applying the item twice.
- Each field declares its application point. The interface shows **applied** or **pending**, with the boundary. Generation settings must also offer an explicit **Restart floor with these settings** action so they can be tested during the same application session. That action visibly restarts the floor; it is not a hidden graph rewrite during combat.

| Parameter category | Required live behavior |
| --- | --- |
| Player movement and safe continuous enemy movement parameters | Apply at the next simulation update; do not teleport actors or change input mapping. |
| Damage, Tears, Shot Speed, Range and newly emitted attack properties | Subsequent attacks use the revision; already emitted projectiles retain their birth properties. Define cooldown transition behavior so editing cannot silently bank extra shots. |
| Enemy attack-pattern/timer parameters | Apply at a documented safe attack/state boundary, displayed as pending until then; provide room retry to see the new pattern immediately. |
| Enemy maximum HP | New spawns use the new maximum. Offer explicit application to living enemies with documented proportional current-HP preservation, including HP-dependent phases; avoid accidental healing-to-full, duplicate death/reward events or changing bosses through the regular-enemy multiplier. |
| Player starting hearts/resources/equipment | Apply on retry/new expedition; editing a starting value does not grant resources mid-combat. A separate explicit reset/retry makes the change testable immediately. |
| Item/stat-effect parameters | Recalculate current supported effects once where safe; stateful effects use their declared boundary. Future offers and existing owned items must not silently follow different undocumented revisions. |
| Room counts, layouts, encounters, shops, pools and reward weights | Newly generated content uses the revision. Preserve already generated/collected/purchased content until an explicit room/floor restart; distinguish stock refresh from buying the same stock twice. |

Every handoff includes one round-trip test: change a newly delivered value, observe the declared effect, export, close/relaunch the main game, load the preset and observe the same effective value. Also restore the reference and repeat the source comparison. Tests must cover rejection without partial application and relevant save/configuration boundaries.

## Order and review boundaries

- D01–D08 are the first sequence: **tune/export → walking → shooting → Gaper → Spider → Pooter → HP/damage → complete combat room**. Movement and firing are reviewed before a live HP verdict, so the previous speed problem is caught early.
- D09–D13 build the reward/shop/upgrade/boss loop on those accepted mechanics. Each lettered entry is one handoff. Choose the exact item/actor/room ID and source evidence before starting that entry; attach it to the existing H/S/E/P/R/X/B/C register IDs rather than declaring the whole family selected.
- D14 connects exact captured placement and procedural floor rules. D15–D17 close the reachable content. Bring a concrete dependency forward when an earlier delivery needs it; do not wait until the end to discover an unsupported required boss summon, starting item or reward.
- D18–D20 accept persistence, alternate opening coverage and the complete first floor. Every intermediate delivery remains enabled in the main game. Temporary narrow coverage is reported in the progress report and cannot be relabelled full parity.
